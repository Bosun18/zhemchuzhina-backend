# API для админки

Документация части REST API отеля «Жемчужина», предназначенной для персонала
(администраторы, директора, разработчики).

> Большая часть административных операций (управление номерами, типами номеров,
> сезонами, ценами, новостями, услугами, галереей, модерация отзывов,
> пользователи, журнал активности) выполняется через **Filament-панель**
> (`/admin`), а не через REST API — отдельная документация по API для них не
> требуется.
>
> Через REST API персоналу доступно только управление бронированиями — это
> нужно, например, для интеграции с внешними клиентами/мобильными приложениями
> сотрудников ресепшена.

## Базовая информация

- Базовый префикс: `/api/admin`
- Формат ответов: `JSON`
- Авторизация: **Laravel Sanctum**, токен передаётся в заголовке
  `Authorization: Bearer {token}`
- Доступ: только пользователи с ролью `admin`, `director` или `developer`
  (middleware `auth:sanctum` + `role:admin|director|developer`)
- При отсутствии токена — `401 Unauthorized`, при недостаточной роли — `403 Forbidden`

## Бронирования

### Список всех бронирований — `GET /api/admin/bookings`

Возвращает все бронирования (от новых к старым) вместе с данными гостя.

Ответ `200`:
```json
[
  {
    "id": 10,
    "check_in": "2026-07-01",
    "check_out": "2026-07-05",
    "guests_count": 2,
    "status": "pending",
    "comment": "Поздний заезд",
    "room": {
      "id": 1,
      "number": 1,
      "type": "Стандарт"
    },
    "user": {
      "id": 5,
      "name": "Иван Иванов",
      "email": "ivan@example.com"
    },
    "admin_comment": null
  }
]
```

Возможные значения `status`: `pending`, `confirmed`, `cancelled`.

### Подтвердить бронирование — `PATCH /api/admin/bookings/{booking}/confirm`

Переводит бронирование в статус `confirmed`. Гостю автоматически отправляется
письмо и всплывающее уведомление о подтверждении.
Ответ `200` — обновлённый объект бронирования (формат как в списке, с данными гостя).

### Отменить бронирование — `PATCH /api/admin/bookings/{booking}/cancel`

Переводит бронирование в статус `cancelled`. Доступно для любого бронирования
(в отличие от `DELETE /api/bookings/{booking}` из клиентского API, здесь не
требуется быть владельцем — достаточно роли персонала). Гостю отправляется
письмо и уведомление об отмене, директора получают уведомление.
Ответ `200` — обновлённый объект бронирования.

> Уведомления при смене статуса (письмо гостю/директору + колокольчик) едины
> для всех путей — API, действий и формы в админ-панели — и срабатывают
> автоматически при изменении статуса брони/отзыва.

### Создать бронирование вручную — `POST /api/admin/bookings`

Используется, например, при бронировании по телефону.

| Поле | Правила |
|---|---|
| `user_id` | required, существует в `users` |
| `room_id` | required, существует в `rooms` |
| `check_in` | required, date |
| `check_out` | required, date, позже `check_in` |
| `guests_count` | required, integer, min:1 |
| `status` | sometimes, одно из: `pending`, `confirmed`, `cancelled` (по умолчанию `confirmed`) |
| `comment` | nullable, string, max:1000 |
| `admin_comment` | nullable, string, max:1000 — служебный комментарий, видимый только персоналу |

Дополнительная проверка (ошибка `422` в поле `room_id`):
- номер не должен быть занят (статус не `cancelled`) на пересекающиеся даты

Ответ `201` — созданное бронирование (формат как в списке, с данными гостя).

> Обратите внимание: проверка вместимости номера (`max_guests`), которая
> применяется в клиентском эндпоинте `POST /api/bookings`, здесь не выполняется —
> персонал может оформить бронирование с любым числом гостей.

## Коды ошибок

| Код | Когда возникает |
|---|---|
| `401` | запрос без токена / с недействительным токеном |
| `403` | пользователь авторизован, но не имеет роли `admin`/`director`/`developer` |
| `404` | бронирование с указанным `id` не найдено |
| `422` | ошибка валидации — тело ответа содержит `message` и `errors` |
